# 验证结果与兼容性

验证日期：2026-10-21。交付版本：0.1.10。下文保留旧版基线，并单独标明本次重跑范围。

## 0.1.10 媒体后缀

用户确认 iOS 上传及安卓接收正常后，报告图片和视频缺少后缀，需手动重命名才能打开。快捷指令发送的媒体名称可能不带后缀，请求统一使用 `application/octet-stream`；旧服务直接沿用这两项，缺失会延续到中转和保存。旧下载响应的 ASCII 兼容文件名也固定为无后缀的 `download`。

本版在系统分享文件接收完成后，根据有界文件头补齐缺失的后缀与类型，完成元数据先持久化再公开；原有后缀保留，未知格式使用 `.bin`。下载的 ASCII 兼容文件名保留安全后缀，完整原名仍通过 UTF-8 `filename*` 返回。文件正文、快捷指令及安卓交互均不改变，也不批量重命名此前已保存的公共文件。

- **85 项核心测试、22 项 Android 模型测试通过**。新增 12 项文件名回归，覆盖 JPEG/PNG/GIF/WebP/TIFF/BMP、HEIC/HEIF/AVIF、MOV/MP4 与音频区分、未知或坏格式、64 KiB 上界、原有后缀、版本尾段、Unicode 长名碰撞、chunked、中转、保存声明及重启。见 `test-evidence/media-filename-core-tests-0.1.10.xml`、`media-filename-model-tests-0.1.10.xml`。签名与容器夹具不等于真实媒体解码测试。
- Release 版本代码 14、最低 API 29、目标 API 37、原项目证书，lint 无错误。快捷指令、全部网页与许可资源，以及 7 份安卓 Kotlin 源码逐字节沿用 0.1.9；核心仅 `TransferServer` 文件名与下载头处理变化，保留 0.1.9 的连接清理修复。
- 源码包在独立目录、不含私钥和本地配置的条件下离线构建 Debug APK，串行通过同一套 85 项核心与 22 项模型测试。见 `test-evidence/media-filename-clean-build.txt`。
- 最终签名 APK 在 API 29、API 34 各通过 28 项、共 **56 项**实服检查，本地与实际安装摘要一致。覆盖 11 类文件名及 MIME、独立客户端下载响应与原字节、临时中转、保存、重启和精确清理；两端原有 36 / 33 条保存记录和 11 / 8 个可读下载文件全部保持。API 34 报告明确区分同包首轮 22 项与 MOV 补验，不将续验冒充完整单轮。见 `test-evidence/media-filename-ui-api29.json`、`media-filename-ui-api34.json`。发送来源为桌面 HTTP 工装，本次未执行实体 iPhone 快捷指令。
- 安卓实服使用有效 PNG/JPEG 与可在桌面解码的 H.264 MP4/MOV 夹具，HEIC 为签名合成字节。PNG/JPEG 检查真实图片查看器；AOSP 模拟器未给 MOV 实际使用的 `video/quicktime` 匹配查看器，MOV 只检查既有分享回退界面、文件名及可读的保存 URI，结合源码核对 MIME 与读取授权配置，不声明实际视频播放或内部授权观测通过。API 34 的 MediaStore 将 MOV 类型规范化为 `video/mp4`，但 `.mov` 名称、长度和原字节保持一致，应用保存记录仍保留原容器类型。

## 0.1.8 文件名编码参数

用户测试 0.1.7 后，小文件显示「文件名无效」，大文件仍持续运行。该服务端错误在解码后的名字为空、`.` 或 `..` 时返回，发生在读取正文之前。独立实际导出及引擎参数资料确认：Get Name 的 `WFInput` 是变量选择器，URL Encode 的同名字段却是文本输入；后者不能使用前者的裸变量封装。新版本只将 URL Encode 输入改为带变量的 `WFTextTokenString`，不生成替代名、不放松文件名检查。

- 全部 38 个动作的配置参数经过独立类型检查；冻结的 0.1.7 错误输入会被拒绝，文本、变量、条件、字典和循环引用分别核对。见 `test-evidence/ios-shortcut-contract-0.1.8.json`；原有 17 项条件回归也通过，见 `ios-shortcut-regression-0.1.8.json`。它们不执行 iOS。
- 新签名的证书链、完整性及完整工作流等价检查通过。APK 版本代码 12、最低 API 29，签名一致，Release 构建和 lint 无错误；相对已发布 0.1.6 只有版本清单、快捷指令资源及构建提交号变化，全部 DEX 与其他资源逐字节相同。见 `ios-shortcut-signature-0.1.8.json`、`ios-shortcut-binary-0.1.8.json`。
- 早拒绝的私有桌面 HTTP 对照确认，同一个空名字错误可能被连接异常遮住，且与正文大小、chunked、Expect 有关；未复现 iOS 持续运行。因此未改动传输内核、接收 UI 或缓存规则，没有把该推断写成大媒体已修复。

**后续用户真机反馈：大小文件均可发送。** 独立快捷指令可直接替换，安卓 0.1.6 / 0.1.7 无须为此重新安装。

## 0.1.2 上传修复与最低系统

用户在实体 iPhone 的 Chrome 和 Safari 上均报告上传停在 2 MiB，而 Android 客户端正常。旧版网页把浏览器发出字节当成接收进度，2 MiB/4 MiB 因此不能证明接收端已经保存了这些字节。另在旧内核独立复现六个空闲 TCP 连接占满工作线程、下一块与状态查询一起等待的问题；这是一项确定缺陷，但尚不能认定为该 iPhone 现象的唯一原因。

- 首次上传改为边读边传并增量计算 SHA-256；仍验证分块和最终完整文件。重选文件续传只核对已经提交的前缀，兼容旧版已声明完整摘要的任务。
- 主进度只统计接收端确认的字节。丢失回复时查询断点并重发同块，服务端做幂等验证；最多自动重试 3 次。暂停和取消可以打断恢复，校验或权限错误不会盲目重发。
- iPhone/iPad 网页单次请求降为 512 KiB，降低单次请求及重试成本；不把它解释成 iOS 的固定大小限制。其他客户端仍最多 2 MiB。
- 请求头改用独立非阻塞就绪阶段，空闲及不完整请求头不占传输线程；上限 48 个待请求头连接、16 KiB/连接和 5 秒绝对期限。修复提前拒绝正文时 TCP 重置掩盖错误回执的问题。
- 最低 Android 调整为 **Android 10 / API 29**，目标 API 37。依据是现有 MediaStore Downloads 保存流程最低需要 API 29；补齐通知权限、待保存项查询和旧系统备份规则。全部核心 Java 源文件通过 API 29 SDK 符号编译检查。
- **26 项核心测试通过**，新增空闲/半请求头连接、并发分块可用性、请求头上界和期限、二进制预读完整性、前缀摘要及其鉴权、重启与清理边界。Android lint 无错误，最终 Release 签名与旧版一致。
- 桌面 Chrome、WebKit 的协议夹具与真实 Java 服务均通过：丢确认、提交前断线、确认前不虚增进度、错误文件和最终损坏拒绝、恢复期间暂停/取消、页面重载及同任务恢复。iPhone UA、iPad 桌面模式特征下通过 512 KiB 首块、最终内容与旧版 2 MiB 断点续传。见 `test-evidence/ios-upload-browser-*.json`、`ios-upload-live-*.json` 及日志。
- 最终同一签名 APK 在 **API 29、API 34 专用模拟器各 14 项检查通过**：覆盖升级保留旧文件、多块接收、前缀摘要、系统下载目录保存、重复副本释放、重启回执和下载内容一致。API 29 从此前兼容实验版覆盖升级，保留 3 个已有文件；这不是华为真机验证。见 `test-evidence/upload-android.json`、`upload-android-api29.json`。
- 桌面 WebKit 模拟 iPhone 特征，直接向最终 APK 上传 **21,750,204 字节 APK**：首次只读 524,288 字节便发出请求；六个空闲 TCP 连接并存时，故意丢弃 2 MiB 后一块的成功确认，自动恢复完成，无须手动重试；最终 SHA-256 和浏览器下载内容均一致。见 `test-evidence/upload-webkit-android.json`。

## 实际大文件

通过真实 HTTP 上传并完整下载 **4,295,032,835 字节**（4 GiB + 65,539 字节）。服务的 Java 堆上限为 **128 MiB**，客户端仅使用有限缓冲；完整文件不进入内存。

测试包含强制结束服务进程、追加未提交尾部、重新配对、恢复凭据检查、截断未提交尾部、继续上传、超过 4 GiB 的已提交前缀摘要，以及超过 4 GiB 位置的 Range 内容核对。最终上传和下载长度、SHA-256 均一致。

最终一次运行摘要：

```text
SHA-256: e3111d957c1dc03414015b5a64fad5b9277998e503a014604f489efb885ca6cd
Range 起点: 4295032771
实际运行: 76 秒
环境: Windows JVM / 实际 HTTP
连接失败重试: 1 次
```

该结果证明当前内核可以处理超过 4 GiB 的数据与偏移，不代表任何手机、存储设备或 Wi-Fi 都能达到相同速度。

网页内置的增量 SHA-256 另外处理了相同长度的数据，与 Node.js 标准加密库结果一致，覆盖 32 位字节/位计数边界，输入缓冲保持 2 MiB。

## 使用边界

HTTP 未加密，仅在可信网络使用。Safari 上传应保持页面在前台。网页中断或刷新后需重新选择文件，从零发送；IP 或端口改变时需重新配对。主机优先复用端口，冲突时会选择可用端口并更新二维码。

Android 保存接收文件期间需要约两倍文件大小的空间，可靠保存后自动释放私有重复副本。保存失败会保留已验证的完整文件并提示重试；批量清理保留等待保存的唯一完整副本，不删除原文件和系统下载目录中的已保存文件。

原生客户端的“暂停”保留断点和临时数据以便重试；“记录 → 清理”经确认后删除闲置断点，单个任务可“丢弃”。自动维护使用 24 小时失活期限、256 MiB 共享闲置目标和 30 分钟近期保护，不构成所有存储的硬上限。应用进程已终止时在下次启动补做清理。

卸载会删除应用私有缓存和设置，已保存的公共下载文件保留。保存过程中被强制终止并立即卸载时，隐藏的未完成 MediaStore 项可能等待系统过期回收；不能承诺所有场景下外部目录立即零残留。

测试入口和复现方法见 [TESTING.md](TESTING.md)。机器可读结果位于本目录的 `test-evidence`。
